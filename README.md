# BIS Standards Recommender — MVP (SIH26108)

An AI-assisted recommendation engine that reads a procurement specification
(pasted text or an uploaded document) and returns:

1. The correct primary Indian Standard(s) for the product.
2. Every allied/normative standard (test method, terminology, code of
   practice, safety) that goes with it — not "may include", always included
   when curated.
3. The current mandatory certification requirement (ISI Mark / QCO /
   Hallmarking), evaluated **as of the tender's delivery date**, not just today.
4. An audit of any standards already cited in the text (withdrawn edition?
   wrong family? missing the recommended standard entirely?).
5. A parameter-conflict check (e.g. a tender stating "Grade Fe 500D" but a
   yield strength of 415 MPa, which is a contradiction).

Every fact returned is looked up from a small, hand-curated, source-linked
database — **nothing is generated by a language model**. That is what "zero
hallucination" means here: it's true by construction, not by a promise in a
prompt. See [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) for why, and
[`docs/DATA_PROVENANCE.md`](docs/DATA_PROVENANCE.md) for exactly how sure we
are about each seeded fact.

**Scope of this MVP: 4 product families**, chosen because each has a real,
checkable numeric requirement and/or certification rule (getting full BIS
standards text requires a paid subscription, so this MVP works from public
metadata about each standard, not the standards' full text):

| Family | Primary standard | What it demonstrates |
|---|---|---|
| TMT / reinforcement steel bars | IS 1786:2008 | Parameter conflict (grade vs. stated yield strength) |
| Ordinary Portland Cement | IS 269:2015 | Parameter conflict on a second, unrelated family (generality) |
| Gold jewellery hallmarking | IS 1417:2016 | Certification-scheme check, set-membership parameter check |
| Wrought aluminium utensils | IS 1660:2024 | **The live example**: multi-order QCO history + as-of-date reasoning |

## 1. What's in this repo

```
backend/    Django + SQLite API — the whole recommendation/audit engine.
            Also SERVES the frontend directly (see config/urls.py + settings.py),
            so a single deployment of this folder is the entire app at one URL.
frontend/   Static HTML/Bootstrap/vanilla-JS UI — no build step. Lives as a
            SIBLING folder to backend/ (../frontend from backend's point of
            view) — keep this folder layout when you deploy.
docs/       Architecture notes, data provenance, evaluation set
```

## 2. Run it locally (10 minutes)

### 2.1 Backend

```bash
cd backend
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python manage.py migrate
python manage.py seed_data         # loads the 4 curated families — idempotent, safe to re-run
python manage.py createsuperuser   # optional, lets you browse /admin/ and see every seeded row

python manage.py runserver
```

Visit `http://127.0.0.1:8000/api/health/` — you should see
`{"status": "ok", "families_seeded": 4, "standards_seeded": ...}`.
Visit `http://127.0.0.1:8000/admin/` (after creating a superuser) to see the
entire knowledge base — this is the single best way to convince a judge you
aren't hiding anything.

### 2.2 Frontend

Because the backend already serves the frontend directly (see below), the
simplest option for local development is: **just open
`http://127.0.0.1:8000/`** after starting `runserver` in step 2.1 — nothing
else to run.

If you'd rather iterate on the frontend with its own live-reloading dev
server instead, that still works standalone:

```bash
cd frontend
python -m http.server 5500
```

Open `http://127.0.0.1:5500`, click the gear icon (top right), and set the
API URL to `http://127.0.0.1:8000/api` (only needed in this standalone mode
— when the backend serves the frontend itself, this is automatic).

## 3. Testing it (including the live aluminium example)

### 3.1 The five built-in examples

Click any "try an example" button in the UI, or `GET /api/examples/` to see
them as JSON. Each is designed to exercise one specific feature:

| Example | What it should show |
|---|---|
| TMT bars — parameter conflict | Grade **Fe 500D** implies a 500 MPa minimum yield strength; the text states 415 MPa → a high-severity `param_conflict` finding |
| **Aluminium utensils — live QCO / as-of-date** | Cites the withdrawn **IS 1660:2009** (current edition is 2024) → `superseded_citation` finding. The certification panel evaluates the real, multi-order QCO history (2024 order → 2025 extension → 2026 order) for a **small enterprise**, and — because the 2026 order's exact small-enterprise date wasn't confirmed in public sources — honestly returns `date_unconfirmed_verify_source` with a caveat, instead of guessing a date |
| Cement — grade vs strength conflict | 43-grade cement requires ≥43 MPa; text states 33 MPa → conflict |
| Gold hallmarking — caratage check | 21 karat is not among the currently-covered caratages → `param_conflict` |
| Vague input | No family-specific keywords → the system **abstains** rather than guessing |

### 3.2 Proving the as-of-date engine live

This is the flagship feature — show it changing in real time as the
hackathon dates pass:

1. Load the aluminium example, set **Enterprise size = Large**, delivery
   period = 90 days, and check the verdict. As of the date this data was
   seeded (27 Sep 2026), the horizon (delivery ≈ late Dec 2026) crosses the
   2026 order's large-enterprise date (1 Oct 2026), so the verdict is
   **"Mandatory by delivery date"**, pointing at the 2026 order.
2. Shorten the delivery period to under ~4 days (so delivery stays before
   1 Oct 2026) — the verdict falls back to the still-confirmed 2025
   Extension Order and becomes **"Mandatory now"**.
3. After 1 Oct 2026 has actually passed, re-run the same query with **no**
   delivery period specified (so it evaluates "today") — the verdict becomes
   **"Mandatory now"** against the 2026 order automatically, with no code
   change. This is the point: the system reasons about *when* a rule
   applies, not just whether one exists.

## 4. Deploying it for free — ONE link, zero setup for the reviewer

The backend serves the frontend directly (Django reads `../frontend/index.html`
at `/`, and WhiteNoise serves `../frontend/assets/*` alongside it — see
`backend/config/urls.py` and `backend/config/settings.py`). That means:

- **One deployment, one URL.** You deploy `backend/` once. The link you get
  back *is* the whole working app — open it in a browser and it works.
- **No CORS, no pasting a backend URL.** The frontend's JS defaults to
  `window.location.origin + "/api"`, i.e. "whatever URL you're looking at,
  plus /api" — since the frontend and API are served from the same origin,
  this is correct automatically. The gear icon exists only for local
  development if you ever run the frontend separately; a reviewer never
  needs to touch it.
- **Nothing to download.** A reviewer clicks your submitted link and the
  full UI loads, backed by a live API, immediately.

### 4.1 Deploy (Render, free tier)

1. Push this whole repo (both `backend/` and `frontend/`) to GitHub — the
   folder layout matters, because the backend looks for `../frontend` next
   to itself.
2. On [render.com](https://render.com) → **New → Web Service** → connect the
   repo → **Root Directory: `backend`** (this is the key setting: Render
   will run inside `backend/`, and the app finds `frontend/` one level up).
3. **Build Command**:
   ```
   pip install -r requirements.txt && python manage.py collectstatic --noinput && python manage.py migrate && python manage.py seed_data
   ```
4. **Start Command**: `gunicorn config.wsgi:application`
5. **Environment variables**:
   - `DJANGO_SECRET_KEY` = (any long random string)
   - `DJANGO_DEBUG` = `False`
   - `DJANGO_ALLOWED_HOSTS` = `your-service-name.onrender.com`
   - `DATA_AS_OF` = `2026-09-27` (or whenever you last checked the seed data)
6. Deploy. Open `https://your-service-name.onrender.com/` — that single
   link is what you submit. (`/api/health/` on the same URL confirms the
   backend; `/admin/` lets a judge inspect the raw curated data.)

**Railway** works the same way (root directory `backend`, same build/start
commands) and additionally runs the Procfile's `release:` line automatically,
so you can skip the migrate/seed part of the build command there if you'd
rather keep it in the Procfile.

### 4.2 The cold-start problem, and what to do about it

Render's (and Railway's) free tier spins a service down after ~15 minutes of
no traffic; the next request then takes 30–60 seconds to wake it. For a
reviewer opening a cold link, that looks like a stalled "Connecting…"
indicator, not a broken app — but you don't want to leave that to chance.

**Right before your judging/review window**, set up a free pinger so the
service is warm when the link is actually opened:

- [cron-job.org](https://cron-job.org) or [UptimeRobot](https://uptimerobot.com)
  (both free) → schedule a GET request to
  `https://your-service-name.onrender.com/api/health/` every 5–10 minutes.
- Turn this on maybe 20–30 minutes before your slot, and you can turn it
  off after — it's not meant to run forever on a free tier, just to keep
  the instance warm for the window when someone will actually click the link.
- Test it yourself first: open the link in a private/incognito window (so
  nothing is cached) a few minutes after starting the pinger, and confirm
  it loads instantly with "Backend connected" and the family/standard
  counts populated in the hero section.

### 4.3 Alternative: separate frontend host

If you'd rather host the frontend on GitHub Pages/Netlify anyway (e.g. to
get a nicer custom-looking URL for the frontend specifically), you still
can — the frontend still works standalone, it just needs the gear-icon API
URL pointed at your Render backend once, saved to that browser's
`localStorage`. This is no longer necessary for a reviewer (the one-link
deployment above already solves that) — treat this as an optional extra,
not a requirement.

### 4.4 One-link submission checklist

- [ ] Open the single deployed URL in an incognito window — the page loads (not a blank/error page)
- [ ] The hero shows "Backend connected" and real numbers (`families_seeded: 4`, standards count) without touching the gear icon
- [ ] All 5 example buttons work end-to-end, straight from that one link
- [ ] `/admin/` (same URL + `/admin/`) is reachable with a superuser so judges can inspect raw data
- [ ] If relying on a cron pinger, it's scheduled to be running during your actual review window

## 5. Where the "innovations" live in the code

| Innovation | File |
|---|---|
| As-of-date compliance (mandatory by delivery, not just today) | `backend/standards/services/engine.py` → `certification_verdicts()` |
| Full, honest order-chain history + "date unconfirmed" caveat instead of guessing | same function, `order_history` + `caveat` |
| Parameter-conflict / internal-inconsistency check | `engine.py` → `_param_findings()` |
| Citation audit: withdrawn edition, wrong family, missing recommended standard | `engine.py` → `_citation_findings()` |
| Trust layer (whitelist-only IS numbers, per-row verification labels, abstention) | `models.py` (`verification` field everywhere) + `extraction.py` → `detect_family()` abstain logic |
| Zero-LLM-dependency correctness (works even with no API key configured) | The entire pipeline: `extraction.py` is pure regex, `engine.py` is pure DB lookups |

## 6. Extending past the MVP (for the finale)

- **More families**: add a `ProductFamily` row + keywords, add `Standard`
  rows, add a per-family grade regex in `extraction.py`'s `GRADE_PATTERNS`
  if the family has grades, add `ParamRule` rows if it has numeric
  requirements. Everything else (retrieval, allied graph, certification
  engine, trust layer) is generic and needs no code changes.
- **Real BIS catalogue integration**: replace the hand-curated `Standard`
  rows with a sync job against BIS's own search/metadata, keeping the same
  schema.
- **LLM as a language layer only** (optional): a model could help parse much
  messier/longer tender documents into the same structured fields that
  `extraction.py` currently gets via regex — but it must never be the
  component that decides which IS number is correct. If you add this,
  keep it behind a feature flag so the deployed demo still works with zero
  external API dependency.
- **Multilingual input**: translate to English before running `extraction.py`
  (e.g. via Bhashini), keep the original text for display.
